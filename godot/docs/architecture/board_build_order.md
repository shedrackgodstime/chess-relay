# Board build order

The staged order for the 3D board, from `game_screen_3d.md`, with the reasoning and
the boundary that has to be settled before the pieces exist.

`board_foundation.md` records why the board cannot currently be drag-rotated and
what the reference prototype did differently. This document is the plan that
follows from it.

## The order, and why

```text
1  board shell      squares, frame, plinth, square <-> world
2  world            camera, environment, key light
3  pieces           shapes, materials, board and tray reuse
4  picking          piece colliders and ray resolution
5  HUD              header, clocks, turn, menus
6  motion           glide, capture, last move, check
7  contract         replace the mock position with Rust
```

Stages 1 and 2 come before 3 because **a piece cannot be judged before there is
real lighting to judge it against**, and lighting cannot be judged before there
is a board to look at. Tuning a piece against Godot's default grey world means
tuning it twice.

Stages 1 and 2 are route-agnostic: they are the same whether the pieces end up
built from CSG scenes, from procedural geometry, or from imported meshes. Only
stage 3 forks, which is why it comes after rather than before.

This is `game_screen_3d.md`'s own order. It is written here with the dependency
reasoning, not to replace it.

## The boundary to settle before stage 3

**No piece enum in GDScript.**

`application_core.md` puts board and piece state in Rust's `chess_core`, and says
of Godot: *"Godot renders the board. Rust decides whether a position and move are
valid."* The contract carries `MoveApplied { move, position, clocks }`.

An `enum PieceType { PAWN, KNIGHT, ... }` declared in GDScript today would be a
second source of truth for piece identity. It would look correct, pass every test,
and disagree with `chess_core` at the first change on either side — which is
exactly the failure the command/event contract exists to prevent.

So:

```text
Rust  ── piece identity arrives over the boundary
            │
            ▼
Godot ── shape lookup:  identity -> geometry
```

Godot maps an identity it is given to a shape. It does not decide what identities
exist. The shape library is a lookup table; the list of piece types is Rust's.

This is cheap to get right now, because nothing has been drawn yet, and expensive
later, because by then six pieces will exist under two sets of names.

## Stage 2: the world

Status: **done.**

The world was already largely here: a `WorldEnvironment` with a custom background
and ambient light, a `DirectionalLight3D` key, three fill lights, and a
`Camera3D` carrying the orbit script. What was missing was the camera actually
receiving anything.

- **The screen root now passes input through.** `Control.mouse_filter` defaults to
  `MOUSE_FILTER_STOP`, so the full-rect root was consuming every mouse event before
  it reached `_unhandled_input`, where the camera does all its input. `IGNORE`, not
  `PASS`, because `PASS` takes the event and hands it to a parent, and there is no
  parent `Control` to hand it to.
- **Touch and pinch are handled.** The camera took mouse events only, so on a phone
  it relied entirely on emulated mouse events and had no pinch at all. It now takes
  `InputEventScreenTouch`, `InputEventScreenDrag` and `InputEventMagnifyGesture`,
  and suppresses emulated mouse rotation while two fingers are down — otherwise a
  pinch arrives as two streams of emulated mouse motion and the board spins while
  the player is trying to zoom.

Both are checked in the UI suite, and the checks restore the camera's position
afterwards. They did not at first, which broke two unrelated checks that share the
camera; a check that leaves shared state changed is a check that makes the next one
lie.

## Stage 1: the board shell

Status: **not started. Attempted and reverted.**

The squares were made into instances of two square scenes, generated by a tool. Two
things were wrong and neither showed in the checks:

- The squares were placed at `y = 0` where the original placed them at
  `BOARD_SURFACE_Y - SQUARE_THICKNESS * 0.5`, so the whole playing surface sat
  0.035 above where it had been, proud of the frame.
- The parity that decides light from dark was taken over 1-based ranks instead of the
  original's 0-based ones, which inverted every colour on the board. a1 was dark
  instead of light.

Both were found by reading the deleted code afterwards rather than before, and both
were invisible to the suite, which counted 64 children and round-tripped
`square_to_world` through `world_to_square`. Neither of those looks at a square: the
first does not care where the squares are and the second is pure arithmetic that
ignores the scene entirely.

So the board is back as it was, and the rule for doing this again is that the
original is read in full before any of it is replaced. A generator that writes a
scene nobody read the previous version of is not an improvement.

Replaces the `_ready()` construction in `board_view.gd`, where 64 squares, a
frame, a plinth, coordinate labels and the input surface are all built in code
and none of it is visible in the editor.

Shape of the result:

```text
board_view.tscn
├── Squares          Node3D        64 instances of square.tscn / square_dark.tscn
├── Highlights       Node3D        overlays, currently four roots, built in script
└── BoardInputSurface Area3D       the picking surface, unchanged

The frame and plinth are still built by board_view.gd, as four raised rails and a
base rather than one slab. The generator writes squares only: a slab is not the
same silhouette, and quietly changing the board's look to suit a generator would
be worse than leaving it where it is.
```

```text
square.tscn
└── Square   MeshInstance3D   one square, its mesh and its material
```

One square scene instanced 64 times, rather than 64 squares described 64 times.
That is the composition rule from *Scenes versus scripts* applied to a repeated
node, and it is the same shape as `PlayerRow` in the UI.

### Materials

Square materials are two, not sixty-four: a light one and a dark one. Which
square gets which is a property of the square's position, not of the square.

This is the same rule that moved the UI colours into `chess_relay_theme.tres`, and
it is why the 3D palette is item 4 of `foundation_tightening` rather than an
afterthought. `Theme` does not apply to 3D materials, so the 3D palette cannot
move into the theme; it needs its own home, decided once, here.

## A note on how the scene is authored

`square.tscn` and the 64 instances in `board_view.tscn` are generated by
`tools/build_board_scene.py`, the way the editor would write them, and the
**generated `.tscn` is what is committed and what runs**. The generator is an
authoring tool, not runtime code: nothing loads it, and the scene is reviewed as a
scene like any other.

This is worth stating plainly because item 2 of `foundation_tightening` is about
not building scenes in script. The distinction that keeps the two consistent is
that the generator writes a file that a person then edits in the editor, rather
than a script that builds a tree every run. Sixty-four hand-typed instance blocks
would be no better maintained than a generator, and would not be reviewable.
