# Player identity and display model audit — 2026-10-09

This note records the identity/display-model gap found during the real
`chess_play_host` → Android Godot integration session. It is an audit result,
not an implementation claim.

## Evidence from the live session

The Rust CLI host generated a fresh endpoint identity, published a rendezvous
code, and the Android build joined with that code. The session exchanged and
co-signed real moves. The output identified the players using values such as:

```text
turn: Black | you: White (b455cea2) | outcome: Ongoing
```

That proves the transport/session currently has stable peer IDs and side
assignments for the match. It also exposes the product problem: `White`,
`Black`, and a short peer-ID prefix are implementation facts, not a complete
player identity shown to a user.

## Current sources of truth

| Concern | Current owner/source | Finding |
|---|---|---|
| Cryptographic player identity | Rust `PeerId`, derived from the Ed25519 public key | Appropriate authoritative identity for signatures and transport binding. Not a suitable default display name by itself. |
| Endpoint identity | Iroh endpoint key / persisted installation seed | Must remain stable for the installation. The standalone CLI helper intentionally creates a fresh identity for each run. |
| Match color | Rust `SessionConfig { white, black }` and signed genesis entry | This is the authoritative color-to-peer mapping. UI must derive color from this mapping. |
| Local color | Rust bridge `my_side()` | Correctly derived from the session, but exposed as a string and commonly displayed without the player attached to it. |
| Opponent color | Rust bridge `side_of_peer()` | Available, but not currently part of a complete participant/display snapshot. |
| Player display name | Godot placeholders such as `Peer %s` and setup-local strings | No durable user profile/name authority exists. This is a single-source-of-truth gap. |
| AI identity | Local AI setup/difficulty paths and presentation strings | AI is a separate presentation path rather than a participant from the same identity model. |
| Result wording | Godot parses formatted Rust reason strings | Fragile. `Resignation { by: PeerId }` does not contain White/Black, causing the wrong winner/defeat presentation. |
| Turn wording | Godot receives a side string such as `white`/`black` | `White to move` is incomplete unless the UI resolves White to a participant name. |

## Confirmed defects and risks

### `IDENTITY-001` — no authoritative user profile/display name

The session has a cryptographic `PeerId`, but there is no profile record that
stores an optional user-selected name. The hub currently creates placeholder
labels (`Peer <id>`), while setup and participant cards receive presentation
strings from the caller. Different screens can therefore name the same peer
differently.

### `IDENTITY-002` — fallback names are not defined

The product requirement allows a user to omit a username, but the fallback
algorithm and ownership are not specified. A fallback must be derived from the
stable installation identity, persisted or reproducible across screens and
restarts, and must not be randomly regenerated when the UI reloads.

### `IDENTITY-003` — participant identity is not a first-class model

The match authority knows `PeerId`, host, White, and Black. It does not expose
one complete participant snapshot containing at least:

- stable participant identity;
- display name;
- participant kind (`human` or `computer`);
- color/role in this match;
- local/remote ownership;
- readiness and presence where applicable.

As a result, screens separately combine peer IDs, colors, labels, and status.

### `IDENTITY-004` — AI does not clearly use the same participant model

The AI side has known configuration (side and difficulty), but the display
identity is not demonstrably generated by the same participant authority as a
human side. AI must be a participant record with a stable reserved identity and
metadata, not a special-case string added by an individual screen.

### `IDENTITY-005` — result facts are converted to presentation strings too early

Rust emits `format!("{reason:?}")`; Godot searches that string for words such as
`White`, `Black`, and `Resignation`. This loses structured ownership. In the
observed session, the host resigned, but the Android presentation reported
Defeat because `_player_won()` could not determine who resigned from the
string.

### `IDENTITY-006` — side-only wording is ambiguous

Messages such as `White wins`, `Black to move`, or `you: White` are not enough
for a multiplayer UI. The UI must resolve the side to the authoritative
participant display name, for example:

```text
Alex (White) wins
Jordan (Black) to move
```

The color remains useful as a secondary label, but it cannot be the only player
identity shown to the user.

### `IDENTITY-007` — the standalone live-test helper has a different identity
path

`rust/src/bin/chess_play_host.rs` creates a fresh signing seed and random code
on every run. This is acceptable for a disposable test host, but it is not the
same identity lifecycle as the application’s persisted installation identity.
The distinction must remain explicit so test observations are not mistaken for
production identity behavior.

## Required single-source model

The target authority should be Rust/application-core data, with Godot acting as
a renderer and intent sender. The minimum model should be conceptually:

```text
Profile
  installation_peer_id: PeerId       // stable cryptographic identity
  display_name: Option<String>       // user-owned, validated, persisted
  fallback_name: String              // deterministic from peer identity

Participant
  identity: PeerId | ComputerId
  display_name: String
  kind: Human | Computer
  side: White | Black
  is_local: bool
  presence: Unknown | Online | Offline | Connecting

MatchResult
  reason: Checkmate | Resignation | Draw | Leave | Disconnect | Abort
  winner: Option<ParticipantIdentity>
  loser: Option<ParticipantIdentity>
  actor: Option<ParticipantIdentity>
```

The exact type names may change, but there must be one authoritative owner and
one conversion boundary. Godot should receive participant/result snapshots or
typed fields, not infer identity by parsing debug strings.

## Fallback-name requirements

If the user has not supplied a name:

1. derive it deterministically from the stable installation identity;
2. use a readable, collision-tolerant format (not a raw long endpoint ID);
3. keep it stable across restarts, screens, and peer-list refreshes;
4. distinguish human fallback names from the reserved computer/AI name;
5. handle collisions in the display layer without changing the underlying ID;
6. validate and persist an explicit username through the same profile owner.

The fallback must not use a fresh random value at render time. A random name
would recreate the identity inconsistency this audit is intended to remove.

## Required UI behavior

Every player-facing surface should consume the same participant snapshot:

- multiplayer recent-peer rows;
- invite dialogs;
- game setup participant cards;
- game header player labels;
- board orientation labels;
- turn indicator;
- check/checkmate result;
- resignation, leave, and disconnect presentation;
- rematch presentation and history.

For example, a result should be resolved from structured ownership:

```text
Alex resigned
Jordan wins
```

not from a heuristic such as “does the formatted reason contain my side?”.

## Verification requirements before this item is complete

- Verify the same installation keeps the same peer identity after restart.
- Verify a saved username appears identically in hub, setup, game, and result UI.
- Verify an unnamed human gets the same deterministic fallback everywhere.
- Verify the AI appears through the same participant contract.
- Verify White/Black names remain correct when either player is host or guest.
- Verify checkmate, resignation, draw, leave, and disconnect identify the
  correct actor, winner, and loser on both devices.
- Verify orientation changes do not change participant identity.
- Verify a peer-ID collision in display names does not merge participants.
- Add Rust contract tests and Godot UI tests for these mappings.
- Run a two-process desktop/Android session and retain the observed output.

## Status

This is a newly recorded audit gap. No identity-model implementation was
changed while writing this document. The live test was successful for
connection and move synchronization, but it also confirmed that result and
player presentation are not yet backed by one complete source of truth.

## Implementation addendum — 2026-10-09

The agreed model was implemented after this audit, in uncommitted working
changes (review with `git status` / `git diff`):

- Rust owns the profile: `PlayerProfile` persisted next to the identity key
  (`set_player_name(name, identity_path)`, one `clean_player_name` rule for
  saves and loads, deterministic `Player <8-hex>` fallback from `PeerId`).
- Rust owns terminal facts: pure `terminal_outcome()` maps session state to
  (reason, actor, winner, loser) by `PeerId`; `result_snapshot()` shapes it
  into the `game_result` Dictionary (`peer_for_side`, `player_name`,
  `my_player_name` for lookups). The resignation-winner case has a Rust
  regression test (`resignation_names_winner_by_identity`).
- Godot renders only: game-over card, clock strip, and hub profile row read
  the structured result; `_end_text` string-sniffing was deleted. The hub
  gained a display-name editor that echoes the Rust authority back.
- Gates at time of writing: `cargo fmt --check`, `clippy -D warnings`, full
  `cargo test` (88 lib incl. 2 new + all integration suites), `cargo doc`,
  and Godot `run_all_checks.sh` (151/151) all green.

Still open from the verification list above: two-device confirmation of the
fixed resignation modal, AI through the same participant contract, and
orientation/peer-collision cases. The `chess_play_host` helper still mints a
fresh identity per run, so it cannot verify installation-stable identity.
